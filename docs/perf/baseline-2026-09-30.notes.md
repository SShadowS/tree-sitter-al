## History of this baseline: the runs that were discarded

Four `baseline` runs on 2026-09-30 were stopped or thrown away before the committed one.
None of their figures is in `baseline-2026-09-30.json`, and nothing was mixed across runs.
What each one did and did not teach:

1. **Under load (about 16:05-16:24).** The machine sat at 29-43% CPU for ten minutes before the start. The load came from another session's jobs: two python processes, `bun test`, and three hung `timeout.exe` processes spinning at about 95% of a core each. The run was stopped when the user cleared them.
   - *Learned:* the start-only 20% rule did warn (41.1%). The native pass also showed 21 `has_error` files in BCApps against the known 2, which was the next run's defect.
   - *Not learned:* how much that load inflated each figure.
   - Afterwards, a process check found no surviving `tools.perf` process.
2. **Stopped for UTF-16 (16:26:11-16:26:44).** The tool read BCApps' 19 UTF-16 HybridGP tables as raw bytes, so each was a whole-file ERROR, and their parse time measured garbage.
   - *Learned:* transcode as `tools/has_error_sweep.py` does (fixed in `caf8446`).
   - *Not checked:* whether a `tools.perf` process survived the stop. This run is the one where that check was skipped.
3. **`tree-sitter generate` exited 1 (about 16:28-16:47:27).** The run died in the build group after 40 minutes of measuring, which ran first then. Its stderr had been captured and dropped.
   - *Learned:* the tool must print the failing command's output (`b9cea71`) and the state it left `src/` in (fix round 1). The build group now runs first, and a finished group is checkpointed.
   - *Not learned:* the cause. It did not recur in three standalone `build` runs or in two later baselines. The review found no concurrent tree-sitter command from any Claude session, and the ts-lock was free.
   - *Remaining candidates, none shown:* a surviving process from run 2, which by its group order would have reached its own build group at about that time; or a non-Claude process holding `src/parser.c` open, such as an editor, Serena or on-access scanning.
4. **Native 20% slow with a clean start reading (16:50-17:20).** This run was committed as `a41f73a` and replaced by `509e6a9`.
   - *What happened:* the native single-threaded passes took 149.1 / 143.9 / 136.8 s, drifting down, against 117.9 s. Parallel was +9%, and dc +16%. The first WASM pass took 79.6 s against 75.5 s. The CPU reading at the start was 10.9%.
   - *Checked:* the slowdown did not reproduce after a generate plus build. Pinning the whole process to CPUs 0-15 and then to CPUs 16-31, on BC.History at about 17:25, gave 22.6 s both times. That was one quiet period: the re-review later measured the two CCDs about 12% apart, and see "CPU placement" below.
   - *Learned:* a reading taken only at the start cannot see a disturbance that arrives after it. The tool now samples the CPU used outside its own process tree for the whole of every group. It also warns when the single-threaded passes spread more than 2%; that run's spread was 9%.
   - *Not learned:* the cause.
   - *Candidates, none shown:* a surviving run 2, whose oracle full tier would have run 31 workers during these native passes; background threads the 2 s reading missed; CPU clock or CCD placement; memory compression (`MemCompression` shows up to a third of a core); on-access scanning.

The committed baseline (`509e6a9`) agrees with an independent `native` re-run: every single-threaded figure is inside its recorded spread, and the combined figures differ by 0.3%.

## CPU placement: the two CCDs measured

`python -m tools.perf.pin` reads the map: CCD 0 is CPUs 0-15 with a 96 MiB L3 (3D V-Cache); CCD 1 is CPUs 16-31 with a 32 MiB L3. The pin is logical CPU 2: physical core 1 of the cache CCD. Core 0 is skipped because it takes interrupt traffic, and its SMT sibling, CPU 3, is not reserved.

Measured on DC (1,352 files), each pass after a warm-up, with the sets visited in rotating order:

| when, 2026-09-30 | pinned to | result |
|---|---|---|
| ~19:25, 5 rounds | CPU 2 / CPU 18 / CPUs 0-15 / CPUs 16-31 | medians 1.747 / 2.002 / 1.725 / 1.932 s: the cache CCD about 12-15% faster |
| ~19:28, 6 rounds, 13 sets | each even CPU, both CCDs | medians 1.533-1.559 s on the cache CCD and 1.559-1.588 s on the other. In rounds 5-6 **every** set ran 15-25% slow at once |
| ~19:38, 10 rounds (`python -m tools.perf.pin calibrate 10`) | CPU 2 against CPU 18 | median 1.538 s (1.529-1.541) against 1.537 s (1.526-1.562): the same speed, and the cache core steadier |

Read together:
- The frequency CCD is never faster on this workload.
- The cache CCD is sometimes 12-15% faster. That happens when the machine is in a slow state, which is the same state as the machine-wide episodes and the ~30% session drift.
- In a quiet period the two CCDs are equal.

Pinning to the cache CCD removes the placement term. It does not remove the machine-wide episodes. That is why decisions use `ab`, which interleaves A and B inside one run.

The AMD 3D V-Cache driver's `Preferences\DefaultType` reads 0 (AMD documents 0 as "frequency"; not verified here). Its live state key needs admin rights and is not read. The power plan is Balanced.

## Compiler sensitivity: the independent review's measurement

The review built the same `src/parser.c` and `src/scanner.c` twice: with MSVC `-O2`, as `tree-sitter build` does, and with clang `-O2` via `zig cc -shared -O2`. It loaded both builds and the repo's `al.dll` into one py-tree-sitter process and timed DC: a warm-up, then three interleaved passes, timing only `parse()`.

| library | DC single-threaded, s |
|---|---|
| MSVC `-O2`, a fresh `tree-sitter build` | 1.527 / 1.529 / 1.538 |
| clang `-O2` (zig cc) | **0.741 / 0.749 / 0.749** |
| the repo's `al.dll` | 1.613 / 1.615 / 1.622 |
| WASM (`perf wasm --corpus dc`) | 1.009 |

- clang is **2.06x** faster than MSVC.
- The two builds produce identical `rows()` trees on all 1,352 DC files.
- The runtime was the same in every case. So the difference is the grammar DLL's own code, not per-call overhead, GC or tree deletion.

This is `docs/deferred-work.md` item 21. The "Compiler sensitivity" section above holds this project's own same-session `ab` measurement of the same comparison.

## Compiler sensitivity: the compiler spike (2026-09-30/10-01)

A spike measured 33 builds of the same `src/`, each against MSVC `-O2`, with `python -m tools.perf ab`. It covered MSVC, clang 23.1.2 (MSVC target), clang-cl, zig cc 0.16 and gcc 13.2, at several levels, with PGO and with LTO. The full report is `.superpowers/sdd/spike-cc/spike-report.md` (git-ignored); the decisions are in `docs/deferred-work.md` item 21.

**Tree identity.** Each of the 33 builds matched MSVC `-O2`'s complete `rows()` trees on all four corpora (70,355 files). A build from an older commit differed, as a negative control. No build is disqualified.

**Speed.** Ratios are time(MSVC `-O2`) / time(build), from 8-round DC runs in one session. Where BC.History was run, it was also 8 rounds.

| clang `-O2` (`-O3`, `-flto`, `-march=native`: all 2.04-2.07) | 2.059 | |
| MSVC PGO (`/GL /GENPROFILE`, then `/USEPROFILE`) | 2.033 | 2.007 |
| zig cc `-O2` | 2.026 | 1.978 |
| gcc `-O2` (`-O3`: 1.962) | 1.935 | 1.913 |

Against clang-cl `/O2`, in 24-round pairs run twice:
- clang PGO: +0.7% to +3.0%, unresolved;
- MSVC PGO: -2%, the two runs agree;
- zig: -1.5%, agree;
- gcc: -5%, agree.

So the compiler decides the speed, and flags and PGO barely matter. MSVC's only 2x path is PGO.

**Build time** for `parser.c` + `scanner.c` to a DLL, median of 3:

| compiler | `-O0`/`-Od` | `-O1` | `-O2` |
|---|---:|---:|---:|
| MSVC | 2.4 s | 13.3 s | 11.3 s |
| clang | 1.8 s | 2.5 s | 2.7 s |
| clang-cl | 1.8 s | 2.6 s | 2.7 s |
| zig cc | 2.3 s | 3.4 s | 3.4 s |
| gcc | 2.3 s | 2.5 s | 2.8 s |

**Build tools.**
- `tree-sitter build` and `tree-sitter test` honour `CC`. With `CC=clang-cl`, a `tree-sitter test` run takes 3.2 s instead of 11.9 s.
- On this machine, `tree-sitter test` rewrites the mtimes of `src/*.c` on every run, so every run recompiles.
- ccache and sccache cannot cache `tree-sitter build`, because it compiles both files in one compiler call.

**Why MSVC is slower (a hypothesis).**
- In every slow MSVC build, `ts_lex_keywords` has a 14,952-byte stack frame. At `-O1` it is 9,224 bytes; at `-Od` it is 232 bytes. clang's is 32 bytes, and the PGO builds have no frame of 4 KB or more.
- Speed follows the frame size.
- Removing the stack probe (`-Gs32768`) changed nothing (1.006), so the probe is not the cost.
- No profiler run was done.
