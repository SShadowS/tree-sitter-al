================================================================================
A block's end buried among statements in a later branch, with an #else
--
Real site: Check.Report.al:1170 and :1198, which are ONE construct -- an `else`
whose block opens in the first region and closes in the second.
.
`_preproc_end_guard` used to be `#if end [;] #endif` and nothing else, which
assumed the closing region contributes the `end` and nothing but the `end`. The
real region contributes a statement, then `end;`, then two more statements, and
carries an `#else` supplying the text for the configuration in which the block
was never opened at all. Widening it needs the declared conflict
[_preproc_end_guard, empty_statement]: the widened rule allows statements after
`end [;]`, and `empty_statement` is itself just `';'`.
.
Isolating this took a mechanical sweep, not reading: resolving each #if region
in turn and reparsing. Region-at-a-time isolation initially blamed BOTH regions
separately, because resolving either one away breaks the pair.
================================================================================

codeunit 50000 T
{
    procedure P()
    begin
        if No < 1 then
            AddTo(Text026)
        else
#if not CLEAN27
        begin
#endif
            for E := 4 downto 1 do begin
                AddTo(OnesText[E]);
            end;
#if not CLEAN27
            AddTo('POUNDS');
        end;

        if No > 0 then
            AddTo('P**')
        else
            AddTo('ONLY**');
#else
        AddTo(Text028);
        AddTo(Format(No));
#endif
        if CurrencyCode <> '' then
            AddTo(CurrencyCode);
    end;
}

================================================================================
A report dataitem whose closing brace is inside a branch
--
Real site: SalesShipment.Report.al:580, closing dataitem `Total2`. The
consequence is visible two lines later: the `trigger` after `#endif` belongs to
the ENCLOSING dataitem in one configuration and to this one in the other.
.
The first model of this was wrong and is worth recording. Reading it as "one
dataitem owning two physical closing braces" -- a brace in the #if branch plus
an alternative brace after #endif -- made the rule consume the ENCLOSING
dataitem's brace, and the file ended one `}` short with a MISSING node at EOF.
What varies is the BRACE, not the dataitem: report_dataitem's closing `}` is
now `choice('}', $.preproc_split_report_brace_close)`.
.
The existing preproc_split_brace_close could not be reused. It is layout-only
(`repeat($._layout_element)`, not report elements) and requires a closing brace
in BOTH branches, which this shape does not have.
.
The nesting was established by walking brace depth mechanically; by eye the
`}` looks like it closes the dataitem two levels out.
================================================================================

report 50000 T
{
    dataset
    {
        dataitem(Outer; "Integer")
        {
            dataitem(Inner; "Integer")
            {
                column(A; ALbl)
                {
                }
#if not CLEAN28
                column(B; BLbl)
                {
                }
            }
#else
                column(C; CLbl)
                {
                }
#endif
            trigger OnPreDataItem()
            begin
                if not ShowIt then
                    CurrReport.Break();
            end;
        }
        dataitem(Next; "Integer")
        {
            DataItemTableView = sorting(Number);
        }
    }

================================================================================
A case statement whose own end lives inside each branch
--
Real site: Check.Report.al:844. The final branch's PATTERN and ':' sit outside
the directive; each branch then supplies that branch's BODY, the CASE's own
`end;`, and the statements that follow the whole case.
.
`preproc_split_case_statement_end` is a SIBLING of case_statement in
_statement_inner, not a `choice()` on case_statement's trailing end_keyword,
and the difference is the entire point. Three ranges cross here:
.
    case .............................. end
    #if ................. #else ................ #endif
                      following stmts        following stmts
.
tree-sitter nodes are contiguous and properly nested, so no tree can show all
three. Hanging this off case_statement would make the post-case statements
DESCENDANTS of a node called case_statement -- a false claim about the program
that naming the child `preproc_split_*` does not repair. They are instead the
explicit `following` field of one conditional branch, which is true in every
configuration.
.
The `;` after `end` is REQUIRED here, not optional. As an optional it was
ambiguous with `empty_statement` and GLR took the untidy reading: the case's
own terminator became the first child of `following`, so anything reading that
field saw a leading empty statement that is not in the program.
================================================================================

codeunit 50000 T
{
    procedure P()
    begin
        case BalancingType of
            BalancingType::Vendor:
                begin
                    Vendor.Get(BalancingNo);
                end;
            BalancingType::Employee:
#if not CLEAN27
                ApplyBalancingTypeOfEmployee();
            end;

            CheckToAddr[1] := PadStr(CheckToAddr[1], 10, '*');
            CheckDateText := UpperCase(CheckDateText);
#else
                begin
                    Employee.Get(BalancingNo);
                end
            end;

            CheckDateText := Format("Posting Date", 0, 4);
#endif
    end;
}
