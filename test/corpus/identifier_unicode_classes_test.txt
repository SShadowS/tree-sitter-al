================================================================================
AL's identifier rule is C#'s, and these five classes were missing from it.
Measured against alc 18.0.37.11445 with a discriminating control on every probe:
alc's start class is `Lu Ll Lt Lm Lo Nl _` and its continue class adds
`Mn Mc Nd Pc Cf`. grammar.js had `[\p{L}_][\p{L}\p{N}_]*`, which omits Nl at
start and omits Mn, Mc, Pc and Cf entirely -- so five kinds of VALID AL, which
alc compiles, were shredded into an identifier plus an ERROR node.
.
Each case below uses the PROPERTY form on purpose. That is the scanner path:
PROPERTY_NAME is decided in src/scanner.c from the generated range tables in
src/unicode_id.h, BEFORE the grammar's own lexer sees the text. Changing the
regex without regenerating those tables makes the two disagree, and the failure
is exactly this -- the grammar lexes the whole identifier while the scanner
stops at the mark and declines, so the property becomes an ERROR. Verified by
doing precisely that: with grammar.js changed and unicode_id.h stale, case 1
below produced `(ERROR (identifier) (integer))`. Regenerating fixed it.
.
`python tools/gen-unicode-id-table.py --check` is the standing guard.
.

================================================================================
U+FEFF is in \p{Cf} AND in the scanner's whitespace set -- and the two agree.
This is the one codepoint where widening the continue class to \p{Cf} collides
with existing behaviour: grammar.js lists /﻿/ in `extras` and
src/scanner.c's is_extra_space() treats U+FEFF as whitespace, both deliberately,
for the BOM. So the same character is simultaneously an identifier continuer and
a skippable extra, and the two components could have split it.
.
They do not. tree-sitter's longest-match makes the identifier win, and the
scanner's read_word_ci consumes U+FEFF through the SAME generated table, so
PROPERTY_NAME spans the same bytes the grammar's lexer would. Verified in six
positions -- BOM inside a property name, at the END of one, between the name and
its `=`, inside a variable name, at the end of one, and after a var attribute --
all with zero errors and consistent spans.
.
ALC AGREES that U+FEFF continues an identifier: `O<U+FEFF>k: Integer;` compiles
(18.0.37.11445, discriminating controls), as do U+200B, U+200C, U+200D, U+00AD,
U+2060 and U+061C. That is why \p{Cf} is NOT excluded here. Do not "simplify"
this by removing U+FEFF from the class or from `extras` -- each is load-bearing
for a different position, and the accompanying negative fixture pins the
consequence.
