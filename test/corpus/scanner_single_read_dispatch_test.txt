A property whose name starts with a prefix of `begin` is still a property
--
Parse states 20 and 22 offer property_name and begin_keyword at the same
position (an object body just after a procedure header). The scanner used to
try `begin` with its own read, which stops on the first mismatching character
with the matching prefix ALREADY CONSUMED; PROPERTY_NAME then started in the
middle of the identifier, saw a digit where it required an identifier START,
and declined. `b1 = 1;` became an ERROR while `x7 = 7;` in the identical
position parsed as a property. `beginx` always worked, because 'x' is a legal
identifier start — which is what made the shape look arbitrary.
================================================================================

================================================================================
A supplementary-plane identifier must not be lexed as `begin`
--
The leading codepoint is U+20062, a CJK Extension B ideograph and therefore an
ordinary identifier start under grammar.js's [\p{L}_][\p{L}\p{N}_]* rule. Its
low 16 bits are 0x62 = 'b'. wint_t is 16 bits on Windows, so towlower()
truncated the codepoint and the scanner matched it as the 'b' of `begin`: the
variable declaration was swallowed into a begin_keyword. The same file parsed
correctly on Linux, where wint_t is 32 bits — the parser disagreed with itself
across platforms. keyword_byte() folds every non-ASCII codepoint to a byte no
keyword contains, so this test pins the same tree on both.
================================================================================
codeunit 1 T
{
    procedure X()
    var
        𠁢egin: Integer;
    begin
        𠁢egin := 5;
    end;
}
