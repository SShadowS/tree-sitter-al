; B6 negatives: statements alc rejects, pinned as deliberate ERRORs (listed in
; tools/deliberate-negatives.txt). alc accepts only assignments and method invocations as
; statements ("Only assignment and method invocation can be used as a statement"); since B6
; (spec docs/superpowers/specs/2026-10-06-expression-statement-narrowing-design.md) the
; parser's _expression_statement is an invocation only, so each case ERRORs on the rejected
; statement. Every case parsed CLEANLY before B6. The ERROR is the assertion.
;
; alc 18.0.41 codes, from tools/alc_probe/cases/expression-statement/:
;   1;                      AL0104  reject-integer.al
;   'abc';                  AL0104  reject-string.al
;   1 + 2;                  AL0104  reject-additive.al
;   + 3;                    AL0104  reject-unary-plus.al
;   -Foo();                 AL0104  reject-unary-minus-call.al
;   not Foo();              AL0104  reject-not-call.al
;   (Foo());                AL0117  reject-parenthesized.al
;   Rec.Get() = true;       AL0117  reject-comparison.al
;   Arr[1];                 AL0117  reject-subscript.al
;   Foo()[1];               AL0117  reject-call-subscript.al
;   Foo() #if A + 2 #else + 3 #endif ;           AL0175 both configurations, torn-call-plus-both-arms.al
;   exit(1) #if A + 2 #else + 3 #endif ;         AL0104,AL0111 both, torn-exit-plus-both-arms.al
;   exit; (a + b);          a parenthesized statement, AL0117 per reject-parenthesized.al;
;                           moved from exit_statement_spacing_test.txt, it still pins the
;                           exit_statement as valueless (no return_value).
;   and(C); ... not(C);     AL0104  reject-stmt-start-{and,or,xor,div,mod,in,not}.al
;   and := true;            AL0104  reject-assign-to-and.al
;   C := and;               AL0224  reject-read-and-in-expression.al
;   Foo() #if A or (2 = 2) #else and (3 = 3) #endif ;  AL0117 both, torn-call-or-both-arms.al
;
; Each torn case has an invalid fragment in EVERY arm, so every configuration is invalid AL
; and the config oracle can classify the case `negative` for all of them. The single-arm form
; (`Foo() #if A + 2 #endif ;`, valid when A is undefined: torn-call-plus.al, torn-exit-plus.al,
; torn-call-or.al) is pinned by the REJECT list of
; tools/config_oracle/tests/test_expression_statement.py instead.
;
; The operator-word cases ERROR through the `code_names` reserved set (grammar.js
; `reserved:`): in code the seven words never lex as an identifier, so the word is a bare
; operator token with nothing to attach to. Inside an ERROR that token is mostly hidden, so
; most trees show only what follows it (`not(C)` keeps a unary_expression, and recovery
; surfaces `in` as an identifier); in every case the ERROR covers the word.
;
; The recovery shape of the three torn cases is incidental: they recover wide (an outer
; ERROR takes the whole procedure, because in recovery the scanner declines every external
; and `#endif` / `end` lex as fragments; .claude/rules/scanner.md, "Error recovery after a
; malformed line is wide"). When a grammar change moves it, re-check only that an ERROR
; still covers the fragments of both arms.
