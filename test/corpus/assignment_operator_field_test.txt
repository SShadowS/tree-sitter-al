================================================================================
All five assignment operators are distinguishable
--
`_assignment_operator` was a hidden rule over a single token, so
field('operator', ...) on assignment_statement had nothing visible to attach to
and was dropped from node-types.json entirely. The bytes belonged to no node,
so there was no text fallback either: these five statements produced
BYTE-IDENTICAL trees, and a consumer doing dataflow read every one of them as a
plain assignment. 22,964 `:=` per 500 files.
--
The field labels below are the assertion. An unlabelled expected tree would
pass on the broken grammar, because the node shape was never the problem.
================================================================================

        i *= 4;
        i /= 5;

================================================================================
assignment_expression carries the operator too, and for_statement's ':=' is a
different token
--
for_statement uses a literal ':=', which is NOT an assignment_operator. That
distinction is why queries/highlights.scm's `":=" @operator` matched only the
for-statement site and never an assignment; the query now captures both.
The token() wrapper on assignment_operator is what keeps the two apart, and
removing it makes the grammar fail to generate.
================================================================================
codeunit 50100 C

    procedure P()

        for i := 1 to 10 do
            j += i;
    end;
